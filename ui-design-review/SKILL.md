## 这个 Skill 做什么

做 UI 设计评审，分两种场景：

- **设计稿评审（Mockup Review）** — 对照需求检查设计稿是否覆盖所有功能
- **实现评审（Implementation Review）** — 逐像素对比设计稿与前端实现

## 何时使用

- 拿到设计稿，要检查它是否覆盖需求
- 前端做完了，要验收视觉还原度
- 需要产出结构化的设计评审报告

不适用：功能逻辑审查、主观审美评价。

## 一、核心原则

- **需求覆盖** — 设计稿必须覆盖需求中的所有功能点
- **像素级精确** — 不放过 1px 偏差
- **状态全覆盖** — 默认、悬停、点击、聚焦、禁用、加载、错误、空、成功
- **场景化思考** — 多设备、多分辨率、多内容长度
- **问题 + 方案** — 每个问题必须附带修复建议
- **不越界** — 只做 UI 视觉与交互审查，不做功能逻辑或审美评价

## 二、评审前置：先确认基准

评审前必须明确"拿什么当准绳"，不要凭个人印象：

- **前台应用** — 读项目的设计规范文件（Design Token、字体、颜色、间距、圆角、阴影、布局）
- **后台系统** — 用对应的设计规范（如组件库规范）

以文件里定义的规范为准，不依赖记忆里的摘要。

## 三、审查维度

### 需求覆盖审查（设计稿评审）

- 功能需求是否完整覆盖
- 用户场景是否都有对应页面 / 状态
- 验收标准是否可在设计中体现
- 数据约束是否反映在 UI 中（必填、字段长度、格式提示）
- 权限控制是否有明确设计

### 视觉审查（实现评审）

- 颜色、字体、圆角、阴影、间距、边框、透明度、尺寸、图标、图片
- 验证是否使用了设计 token，而非硬编码色值
- 验证深色模式下 token 是否切换正确
- 验证字体本地化（不走外部 CDN）、字号阶梯合规
- 验证文案规范（框架语言与用户内容的区分）

### 交互审查

覆盖九种状态：默认、悬停、点击、聚焦、禁用、加载、错误、空、成功。

### 响应式

- 优先检查主要使用场景（如移动端竖屏 390px），再桌面
- 桌面端（≥1280px）、平板（768-1279px）、移动端（<768px）
- 移动端零横向溢出、输入控件字号 ≥16px（防 iOS 自动缩放）、底部导航固定

### 边界情况

超长文本、空数据、特殊字符、网络延迟。

## 四、三层面走查框架

审查维度决定**查什么**，这个框架决定**从什么角度分析**。

### 1. 本能层 — 用户对界面的第一感知

- **视觉吸引力** — 色彩、质感、动画
- **情感共鸣** — 品牌调性、氛围营造
- **第一印象** — 精致感、专业度

### 2. 行为层 — 任务流程的流畅度

- **任务流程** — 步骤清晰、路径最短
- **交互反馈** — 状态明确、响应及时
- **容错设计** — 错误预防、错误恢复
- **操作效率** — 快捷方式、批量操作

### 3. 反思层 — 功能是否符合真实需求

- **价值感知** — 功能是否解决真实问题
- **个性化** — 是否支持用户定制
- **成就感** — 是否提供正向反馈

## 五、问题分级

| 等级 | 说明 | 处理要求 |
|---|---|---|
| P0 | 需求缺失、布局错乱、功能不可用、严重视觉偏差（品牌色错误、字体未本地化） | 必须修复，阻塞发布 |
| P1 | 需求部分缺失、样式偏差 >2px、交互缺失、信息层级错误、token 未正确使用 | 必须修复，发布前完成 |
| P2 | 1-2px 偏差、色值轻微偏差（<5%）、非关键状态缺失 | 建议修复，下一迭代 |
| P3 | 体验优化、性能建议、最佳实践 | 仅供参考，非强制 |

## 七、约束

**禁止：**

- 功能逻辑审查
- 主观审美评价
- 无设计稿时审查实现
- 无需求文档时审查设计稿

**必须：**

- 先确认系统类型，选对应规范参照
- 设计稿评审需对照需求检查覆盖
- 实现评审需对照设计稿逐像素对比
- 截图标注差异位置
- 每个问题给出修复方案
- 问题分级标注
- 报告结构完整
