## 这个 Skill 做什么

把一份大需求拆成一组**独立、可测、足够小**的用户故事，每条附优先级、故事点数、验收标准、依赖顺序，让人能照着实现、排期、验收。

## 何时使用

- 需求评审通过之后，进入开发拆分 / 排期
- 一个需求太大，需要拆成可独立交付的小块
- 需要给一批需求估点、排优先级、看依赖顺序

不适用：还在写需求文档时；具体编码时。

## 一、每条故事的输出结构

默认含以下字段，某项确实没有就写"无"，不留空引人猜。

1. **编号 + 标题** — `[US-N] <动宾短语>`，一句话说清"给谁加什么"
2. **角色-目标-价值** — `作为 <角色>，我要 <能力>，以便 <价值>`
3. **优先级 / 风险** — P0-P3，并标注是否**核心链路**（决定测试深度与回归范围）
4. **故事点数** — 相对估算，写明依据
5. **功能验收标准** — Given-When-Then 或可勾选 checklist；每条标注优先级与是否可自动化
6. **非功能与护栏验收（按需）** — 权限边界、幂等并发、性能基线、兼容性、隐私护栏
7. **依赖 / 前置** — 依赖哪条故事、哪个域；排期顺序
8. **实现面** — 涉及哪些模块、是否需迁移、接口路径与数据实体
9. **来源** — 需求文档的具体条款 **+ 版本锚点**（需求是活的，不带锚点故事会漂移）
10. **可测试性自检** — 契约已定义？错误码明确？依赖可 mock？日志可观测？

大需求先拆 **Epic → 故事**；每条故事必须是用户可感知的价值，不是技术任务。

## 二、故事点规则（相对估算）

- 用 Fibonacci 序列：**1 / 2 / 3 / 5 / 8 / 13**；常态目标 **≤3 点一条**
- 只做**相对**比较：拿一条已知的小故事当基准（如"展示一个列表 = 2"），新故事与之比大小
- 每条点数写明依据，至少覆盖三方面：
  - **复杂度** — 逻辑、集成、状态流转有多绕
  - **工作量** — 涉及面（前端/后端/表/接口）多大
  - **不确定度** — 需求、技术、依赖是否清楚
- **13 点以上的故事必须再拆** — 那说明它还是个 Epic
- **技术不确定度高时单列 spike**（限时调研，产出结论而非功能），不把不确定度折进点数
- 点数是**规模，不是工期**；不把人天直接当点数

## 三、验收标准格式

每条故事至少 1 条功能验收标准；有状态流转、边界、异常的多写几条。两种写法选一种，同一份清单保持统一。

**Given-When-Then：**

```
- [P0, 可自动化] Given <前置>, When <动作>, Then <可观察结果>。
```

**可勾选 checklist：**

```
- [ ] [P0, 可自动化] <可测结果>
- [ ] [P1, 手工] <可测结果>
```

硬要求：

- 每条都能被中立的人**客观判定**达成 / 没达成，不写"体验良好""性能不错"
- 覆盖**正常路径 + 边界 + 异常**（空值、越权、并发、幂等，视故事而定）
- 与需求条款挂钩（注明来源），便于追溯与写测试

## 四、非功能与护栏验收（按需）

故事点估的是"实现规模"，不等于"测试风险与深度"。以下维度按故事实际触及勾选，落成验收标准：

- **权限 / 越权** — 谁能读写、越权返回什么
- **幂等 / 并发** — 写操作要幂等键、并发撞车的口径
- **性能** — 是否需压测、性能基线
- **兼容性** — 多端、多浏览器、数据迁移前后
- **隐私护栏** — 涉隐私必列，原样承接需求文档

## 五、可测试性自检（写验收标准前）

产出"可验收但测不了"的故事 = 返工。写之前先过一遍：

- 接口**契约已定义**？没有先补契约
- **错误码明确**？引用公共错误码表
- 外部依赖**可 mock**？
- 关键路径**日志 / 审计可观测**？

## 六、拆分原则（INVEST）

每条故事尽量满足：

- **Independent 独立** — 尽量不依赖另一条未完成的故事；有依赖就显式写出顺序
- **Negotiable 可协商** — 只要价值与验收不变，实现方式可讨论
- **Valuable 有价值** — 对用户或业务有可感知价值
- **Estimable 可估算** — 团队能给出点数
- **Small 足够小** — 能在一个迭代内交付，拆到 13 点以下
- **Testable 可测** — 有明确验收标准

两条纪律：

- **角色真实** — 角色取自需求文档的"用户与场景"，不虚构
- **禁止用技术任务冒充用户故事** — "建一张表""加一个接口""抽一个组件"是实现任务，放进故事的实现面或依赖备注。横切关注点（鉴权、幂等、限流、脱敏、审计、迁移回滚）因此易被挡在清单外，用上面「非功能与护栏验收」兜住，而不是硬塞成故事

## 七、FR ↔ US 覆盖检查

输出末尾附一张映射表，挡住"漏一个需求点 = 上线少一个功能"：

| 需求条款 | 覆盖故事 |
|---|---|
| §FR-2.6 | US-3 |
| §FR-2.7 | （缺） |

- 每个需求点 **≥1 条故事**；每条故事 **≥1 个需求点**
- **孤儿两边点名**：无故事覆盖的需求点、无来源的故事，逐条列出并说明（是 Non-Goal？还是漏了？）

## 八、可复制模板片段

```markdown
## [US-N] <动宾标题>

- 作为 <角色>, 我要 <能力>, 以便 <价值>。
- 优先级 / 风险: <P0-P3>; <是否核心链路>
- 故事点数: <1|2|3|5|8|13> (依据: 复杂度 <> / 工作量 <> / 不确定度 <>)
- 验收标准:
  - [<P0-P3>, <可自动化|手工>] Given <前置>, When <动作>, Then <结果>。
  - [ ] [<P0-P3>, <可自动化|手工>] <可勾选的可测结果>
- 非功能与护栏: <越权 / 幂等·并发 / 性能 / 兼容性 / 隐私护栏; 无则写"无">
- 依赖 / 前置: <故事编号 / 域 / 接口; 排期顺序>
- 实现面: <涉及模块 + 是否迁移>; 接口 <路径>; 数据 <是否新实体>
- 来源: <需求文档> §<条款> @ <版本 / 锚点>
- 可测试性自检: <契约 / 错误码 / mock / 日志>
```

## 九、再估 / 重拆

实现中发现拆错（点估偏了、故事该合该拆、依赖翻转）时：

- 在评论里说明新点 / 新拆法与原因，**通知相关方**，留痕
- 不静默改清单 —— 点数是排期输入，静默改会让容量账对不上

## 十、边界

- **不改需求本身** — 拆分中发现需求缺口，提出来，不改需求文档正文；要改需求先回到需求流程
- **不写代码** — 只拆故事、估点、写验收标准
- **不把技术任务当故事** — 建表、加接口、抽组件作为实现面或依赖备注
- **下游衔接** — 拆分产出的验收标准可直接喂给测试用例生成，打通"故事 → 用例 → 执行"的证据链
