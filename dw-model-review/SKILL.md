## 这个 Skill 做什么

用 **MCCL 现行规范** 评审离线数仓的模型设计文档与脚本。与 `dba-schema-review` 的区别：

| | `dba-schema-review` | `dw-model-review` (本 skill) |
|---|---|---|
| 技术栈 | Postgres 类，DDL/迁移/索引 | 盘古调度 + Hive + Spark SQL |
| 主键 | 时间有序 UUID (UUIDv7) | 未强制，但要求明细主键唯一 |
| 时间列 | `timestamptz` + `_at` | `string` + `bi_*` 分区字段 |
| 枚举 | `text + CHECK` | 业务常量集中脚本头部 |

**两套体系不可混用。** 不要拿 UUIDv7 / `timestamptz` 的要求去评 Hive 表。

## 何时使用

- 评审 DWD / DWS / ADS 建表设计文档
- 评审 Spark SQL 脚本
- 评审盘古工作流、调度任务配置

不适用：物理库 DDL、索引、迁移脚本（用 `dba-schema-review`）；概念数据模型（产品需求层面）。

## 一、文档完整性（基础评审，必查）

`08.数据模型和指标评审标准` 要求设计文档必须包含 7 项。**缺项即为阻塞**：

- [ ] 需求背景
- [ ] 业务口径
- [ ] 血缘依赖
- [ ] 字段说明
- [ ] 更新频率
- [ ] 数据量预估
- [ ] 安全等级

常见缺项（实测高频）：安全等级留空或填错、迭代记录空、稽核规则留模板占位、数据模型关系空。

**模板残留也要查**：`XXX表设计` 这类占位标题、上一份文档的截图、无关章节（如 Redis 缓存、"商品评价信息总览"）。这些会让人分不清哪些是真实设计意图。

## 二、分层与命名

### 分层

- 库名遵循层级前缀：`ods_` / `dwd_` / `dws_` / `dim` / `ads_` / `dm_` / `dmd_`
- 一个 L1 主题域一个库
- 表必须落在本域 schema，不得裸放公共库

### 表命名

格式：`库名.L2主题域_业务场景_数据含义自定义_[e]_分区周期`

- 表名**全集群唯一**
- 不推荐 `t_` 开头（失去区分度）
- 不推荐把 `ext`、`csv`、`unc`、`inr`、`pqt` 等技术词放进表名
- 后缀表类型：`d`(日增量) `ed`(日全量) `m`(月增量) `em`(月全量) `w`/`ew` `h` `td`(维表) `his` `tmp` `rt` `pr` `mskd`

### 字段命名

**分区字段强制用 `bi_*` + `yyyyMMdd` 字符串**：

| 周期 | 字段名 | 格式 |
|---|---|---|
| 年 | `bi_year` | yyyyMMdd (1月1日) |
| 季 | `bi_quarter` | yyyyMMdd (季度第1个月1日) |
| 月 | `bi_month` | yyyyMMdd (**每月1日**) |
| 周 | `bi_week` | yyyyMMdd (默认周一) |
| 天 | `bi_dt` | yyyyMMdd |
| 小时 | `bi_hour` | yyyyMMddHH |

> [!warning] 月分区常见错误
> 月分区必须用 `bi_month` 且值为**该月 1 日**。把它写成 `bi_dt`（日粒度命名）会造成语义歧义；值填成月末或月中日期都不合规。

### 任务与文件命名

- 项目：`ADS_L1_L2简称` / `DW_L1_L2简称` / `DW_DIM` / `ODS_来源系统`
- 工作流：`最终目标表名`
- 调度任务：`<任务类型>_<目标库名>_<目标表名>`，任务类型如 `SPARK`/`HIVE`/`DATAX`/`PY`
- 代码文件：`<库名>_<目标表名>.sql`，文件名**统一大写**，扩展名小写，编码 UTF-8 无 BOM

## 三、Spark SQL 强制条款

`离线规范` 第三章为强执行规范，**代码评审一票否决**。逐条对照：

### 通用写法

- **禁止 `SELECT *`**，必须指定字段名 + 表别名
- 产出表字段顺序必须固定，禁止随意增减调换
- 业务常量（状态值、类型值、固定文案）统一在**脚本头部定义**，禁止分散
- **禁止隐式类型转换**：关联/判断字段类型必须一致，关联前显式 `cast`
- 生产脚本禁止无意义 `Limit`（仅自测可用，上线前删除）
- **生产脚本禁止 `WITH`**，需写成子查询；多处引用用临时表
- 所有表必须有别名，且**禁用 `a`/`b`/`c`/`t1`/`t2`/`t3`**，用有含义的别名

### 代码编排

- 文件头必须含 `--@Output` / `--@Input` / `--@Development History`
- 每步 SQL 前加注释；有计算逻辑处（多字段运算、函数、`case when`）**强制加注释**
- 注释说明**为什么这么写**，不要复述代码逻辑
- 关键字大写、缩进统一 4 空格（禁 TAB）、`case` 必须有 `else`
- 一个字段独占一行

### 调度任务

- 建表必须用 hiveddl 组件，**严禁在调度任务中建表**
- **一个节点禁止产出多张结果表**
- 严格限制不同节点写同一张表；如有需求须为分区表且只写不同分区
- 来源表超过 10 张需负责人评审
- 禁止每次回刷全量历史分区；大表须平台负责人审核资源

### 子查询

- 嵌套层次限 **2 层**（复杂情况 3 层），多层建议改临时表
- 禁止子查询 `SELECT *`、禁止不写别名
- **禁止在大表外层用 `NOT IN`/`IN` 子查询**
- 禁止在 `SELECT` 中使用子查询

### 表连接

- 禁止隐式 JOIN，必须指定关联方式和关联字段
- 优先 `INNER JOIN`/`LEFT JOIN`；**禁止 `RIGHT JOIN`**；无必要禁用 `FULL OUTER JOIN`
- 大表驱动小表：`FROM` 先放主大表
- 一个 SQL 连续 JOIN **不超过 5 张**；事实大表关联**不超过 2 张**
- 大表 JOIN 前先做分区过滤
- **禁止直接关联全量分区大表**，用「上一周期结果 + 增量」替代
- 关联前必须确认被关联表主键；一对多时从表先预聚合/去重

### 临时表

- 命名 `tmp.目标表名_序号`，**严禁用来源表命名**
- 计算中先 `drop` 后 `create`，禁止直接用历史调度日期的临时表
- 禁止跨节点使用临时表
- 存储格式 parquet
- **敏感字段不建议存临时表；如必须，则必须加密**

### 性能与倾斜

- 热点 Key（空值/0/默认值）必须加盐打散
- 小表关联大表必须开启广播 join；禁止大表广播
- **分区裁剪最大化**：多分区查询必须**前置分区过滤再关联聚合**，禁止先关联后过滤
- 避免重复计算，同一子逻辑用临时表
- 先过滤再聚合，减少 shuffle

### 落地

- 存储必须 parquet
- 单文件 128M–256M，禁止 KB 级小文件
- 写入模式 `insert overwrite partition`
- 过期分区必须配置自动清理

### 容错

- **空结果容错**：脚本必须兼容当日无数据、上游为空；不能容错的必须有告警机制
- **异常值拦截**：极端数值、非法时间、乱码必须前置过滤，禁止写入正式层
- 事务一致性：重跑不得影响历史分区

## 四、盘古调度配置

- 依赖上游必须配置**精准任务依赖**，**禁止用固定时间做依赖**
- 禁止配置分钟级、随机调度
- 必须配置统一超时时间、重试次数、重试间隔，禁止无限制
- 核心任务必须开启失败告警、超时告警
- 失败后禁止频繁手动重跑，先排查后重跑并登记
- **严格按分层依赖 `ods→dwd→dws→ads`**，禁止跨层、逆向依赖
- 禁止循环/无效/冗余依赖
- 数据输出节点建议单独工作流
- 依赖失败策略建议配置为等待（如 120 分）

## 五、数据质量四校验

所有上线任务必须配置基础质量校验：

| 校验 | 要求 |
|---|---|
| **非空** | 核心主键、时间、业务状态字段禁止为空 |
| **量级** | 每日数据量波动（暴涨/暴跌）需排查，禁止直接上线 |
| **主键唯一** | 明细数据必须保证主键唯一，避免重复计算致指标失真 |
| **口径一致** | 改历史脚本后必须对比修改前后指标差异 |

> [!tip] 稽核规则表不接受模板占位
> 文档里"XX表/指标要求在XX时间之前出数"这类文字是模板示例，不是规则。评审时必须要求填**具体到本表**的规则，并按强/弱依赖标注。

## 六、安全合规

`08.数据模型和指标评审标准` 把"安全合规"列为独立评审分类，含三项：**安全等级定义、敏感信息、加密字段**。

### 两套体系，不能互相替代

| 体系 | 面向 | 判断什么 | 填在哪 |
|---|---|---|---|
| **数仓安全等级** (五级) | 库表资产 | 泄露对**公司**的影响 | 设计文档"安全等级"栏 |
| **个人信息分级** (四级) | 字段内容 | 泄露对**个人**的影响 | 决定字段是否加密脱敏 |

一张表可以整体定三级，但表中某字段因含个人信息仍需脱敏。

### 数仓安全等级五级

| 等级 | 定义要点 | 常见示例 |
|---|---|---|
| 安全一级 (绝密) | 严重影响业务、国家安全、人身财产安全，或触犯法律 | 未脱敏证件号/银行账号/手机号/邮箱；员工薪酬 |
| 安全二级 (机密) | **严重**影响业务、损害声誉和营收 | 未对外披露的**核心经营指标** |
| 安全三级 (秘密) | **影响**业务、损害声誉和营收 | 餐厅、订单、促销、**供货商** |
| 安全四级 (一般) | 损害公司声誉 | 内部公开的**渠道编码、商品信息**、码值映射 |
| 安全五级 (公开) | 无负面影响 | 天气、日历、行政区划、已公开经营信息 |

**定级过高或过低都是问题。** 定低了掩盖脱敏义务（四级对应个人信息第 1 级低敏感级），定高了会过度限制访问。

### 个人信息分级与脱敏

| 个人信息分级 | 对应数仓等级 | 典型类别 |
|---|---|---|
| 第 4 级 极敏感级 | 安全一级 | A1-4 实体身份证明、A2-1 鉴权信息、B3-1 金融账户、C3-2 精确位置、D 未成年人 |
| 第 3 级 敏感级 | 安全一级 | **A1-1 个人基本资料（含姓名）**、A1-2 身份标识、**A1-3 网络身份标识**、B2-2 个人工作信息 |
| 第 2 级 较敏感级 | 安全二级 | B3-2 个人交易信息、C3-1 粗略位置、C4-1 个人标签 |
| 第 1 级 低敏感级 | 安全三级 | 其它 |

**入仓原则**（关键）：没有分析价值的敏感信息**不入仓**；有分析价值的**只落 ODS**，提取到 ODS 之上**需做加密或脱敏**。

> [!warning] DWD / DWS / ADS 层都要查脱敏
> 这三层都在 ODS 之上。看到明文姓名、工号、手机号、身份证号即可判为违规，不是"待确认"。

**规范脱敏方式**：

| 类别 | 方式 |
|---|---|
| 个人姓名 | 两字名：第二字换 `*`；三字及以上：保留首尾，中间换 `*` |
| 个人证件号码 | 保留前 4 位，其余换 `*` |
| 住址 | 保留到省 |
| 设备识别码 / 网络身份标识 | 保留前 4 位，其余换 `*` |

必须加密存储的字段：手机号等个人电话、用户鉴权信息、身份证件、金融账户、地址、车牌号、邮箱、未成年人所有信息。

## 七、评审产出

### 必须给出条款出处

结论要能追溯到规范。不要写"不符合规范"，要写：

> 违反《离线规范》3.3.1「禁止使用 `SELECT *`，必须指定字段名，且必须指定字段出自哪张表即表别名」

### 分级

`离线规范` 第八章已有违规分级，直接映射：

| 规范档位 | 对应 | 示例 |
|---|---|---|
| 轻度 | P2/P3 | 命名不规范、无注释、格式混乱 |
| 中度 | P1 | `SELECT *`、无分区过滤、硬编码时间/参数、依赖混乱、资源乱配 |
| 重度 | P0 | 未自测上线、私自改线上脚本、口径错乱、导致数据故障 |

### 报告格式

```
结论: <通过 / 要求修改>
依据: <规范名 + 条款号 + 链接>

要点:
- [表名.字段名] <问题> → <修法> | 违反 <条款>
- ...

未能确认: <需要作者或数据安全确认的点>
```

**未能确认的点必须单列**，不要混进结论。典型：上游是否已脱敏、定级是否有未写出的依据、规范是否已改版。

## 八、评审前自检

- [ ] 7 项文档完整性字段齐全
- [ ] 无模板残留（占位标题、他人截图、无关章节）

- [ ] 分区字段用 `bi_*`，月分区用 `bi_month` 且值为每月 1 日
- [ ] 无 `SELECT *`，所有表有含义化别名
- [ ] 无 `WITH`、子查询 ≤2 层、无 `NOT IN` 大表子查询
- [ ] 无 `RIGHT JOIN`、连续 JOIN ≤5、大表关联 ≤2
- [ ] 分区过滤前置，未直接关联全量分区大表

- [ ] 临时表命名 `tmp.目标表_序号`，未跨节点
- [ ] 调度用精准任务依赖，非固定时间
- [ ] 超时/重试/告警已配置
- [ ] 分层依赖符合 `ods→dwd→dws→ads`
- [ ] 数据质量四校验齐全，无模板占位
- [ ] 安全等级已定且定级合理
- [ ] 敏感字段已加密/脱敏（DWD 及以上层）

## 九、边界

- 只评**物理设计与开发规范**，不评业务语义是否合理
- 概念数据模型（有哪些实体、什么关系）属产品需求层面
- 库表权限审批、实际数据值核对不在本 skill 范围
- 定级争议（如是否升二级）应交数据安全/DCO，不要自行判定
