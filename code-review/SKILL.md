## 这个 Skill 做什么

给数据类代码加一层评审视角。适用于 **Spark SQL / HiveSQL 脚本**和 **Python 数据任务**（拉数、导表、推消息）。

目标不是找语法错误——那些编译器会报。目标是找**能跑通但结果错、或者静默失败**的问题。数据任务里最贵的 bug 是任务返回成功、下游没人发现。

## 何时使用

- 评审 MR、分支、或某个目录的代码
- 评审单文件脚本（`spark.sql`、`etl.py`、定时任务脚本）
- 有人问"这段逻辑对不对"、"帮我看看有没有问题"

不适用：DDL 与数据模型变更（用 `dba-schema-review`）；业务口径是否合理（那要找需求方，本 skill 只标出"这里需要业务确认"）。

## 核心原则

1. **先建上下文，再下判断**。孤立看一个文件容易误判。ETL 脚本通常有上下游——读一下上游怎么产数、下游怎么消费，很多"看起来奇怪"的写法其实是约定。**没读上游就不要下 P0 结论。**
2. **区分"错误"和"待确认"**。拿不准是 bug 还是业务口径时，列进"待业务确认"，不要硬判成 bug。
3. **每条问题必须能定位**，给出 文件:行号 + 代码片段。
4. **按后果分级，不按代码风格分级**。能静默产出错数据的排 P0，命名不好看的最多 P2。

## 评审流程

### 第一步 · 拿到代码和一个完整上下文

不要只看目标文件。至少额外拉取：

| 文件类型 | 该拉什么 | 为什么 |
|---|---|---|
| ETL SQL | 上游产数脚本、下游消费脚本 | 判断字段语义、分区约定、NULL 可能性 |
| ETL SQL | 同仓同类任务的脚本 | 判断某写法是笔误还是全仓约定 |
| Python 脚本 | README / 配置文件 | 代码与文档是否一致；配置项实际含义 |
| 任意 | git log / 最近提交 | 判断代码是新增还是历史遗留，影响"是否该在本 MR 修" |

读上游的价值：比如看到 `NOT IN (select ... from xxx)` 没有分区过滤，只有对比同仓另一个任务才发现是漏写。

### 第二步 · 分类排查

按下面的清单逐类走。**不要跳着看**，人眼容易只盯着自己熟悉的类别。

### 第三步 · 分级输出

按"产出格式"一节写结论。

## 一、SQL 正确性清单（优先级最高）

### 1. `NOT IN` 与 NULL

子查询返回任何 NULL 时，`NOT IN` 对主表每一行都返回 UNKNOWN → **结果集静默为空**，任务成功。

```sql
-- 危险
where cardsn not in (select cardsn from some_table)

-- 三种改法，按场景选
where not exists (select 1 from some_table t where t.cardsn = a.cardsn)
where cardsn not in (select cardsn from some_table where cardsn is not null)
where cardsn not in (select nvl(cardsn, '') from some_table)
```

同时检查子查询**有没有分区过滤**。没有则全表扫描，且在大表上随分区增长越来越慢。

### 2. 窗口函数与 `where` 的执行顺序

窗口函数在 `where` 之前求值。所以下面这段的实际语义是"先取最新一条，再判断余额>0"，而不是"在有余额的记录里取最新一条"：

```sql
select *, row_number() over (partition by id order by ts desc) as rn
from t
where rn = 1 and balance > 0   -- 先 rn=1，后 balance>0
```

问清楚业务要的是"最新快照满足条件"还是"历史上存在满足条件的记录"。二者结果不同，且都"看起来对"。

### 3. 主键 / 去重键的稳定性

`md5(concat(...))` 造主键时检查：

- **无分隔符拼接会撞键**：`concat(a, b)` 里 `a='AB', b=''` 与 `a='A', b='B'` 同值。改用 `concat_ws('|', ...)`。
- **金额、浮点、时间参与拼接**：格式化方式一改，同一笔业务的主键就变了，下游去重失效。日期要固定格式（用 `date_format` 显式指定，不要依赖列的原样字符串）。
- **带 `updated_time` 之类的"最后修改时间"造业务主键**：这是最常见的设计错误——同一个业务对象每次更新都会产生新键。

### 4. 分区与写入

- `insert overwrite ... partition (dt)` + select 里又有 `'${dt}' as dt`：要求 select 最后一列恒等于分区值，否则报错或写错分区。属既有风格时提示即可，但新增代码要统一。
- `drop table if exists x; create table if not exists x as`：`if not exists` 是冗余的；更实际的危害是当 `drop` 失败（权限、并发）时，`create if not exists` 会**静默复用旧表结构**，随后 `insert overwrite` 写入不匹配的数据。建议去掉 `if not exists` 让失败暴露。
- 上游改列顺序时，靠位置对齐的多分支 `union all` 会静默错位。检查是否可用显式列名约束。

### 5. 日期与格式

- `regexp_replace(x, '-', '')` **默认只替换首个匹配**。跨月比较前先确认输入格式真的只有一个分隔符。
- 无分隔符的 `yyyymmdd` 字符串比较是安全的（字典序 = 日期序），**不要误报**。
- `substring(date_str, 1, 10)` 这类截断，在带时区或带毫秒的输入上会错。

### 6. 关联与聚合

- `inner join` 是否会把"本次业务本不该出现的记录"过滤掉？left→inner 的改动要特别问。
- `left join` 后 `where` 里过滤右表字段，等价于 `inner join`——是笔误还是有意？
- `count(*)` vs `count(distinct)` vs `sum(...)` 在 join 放大后是否重复计数。

## 二、Python 数据任务清单

### 7. 资源泄漏

```python
# 危险：句柄无人关闭
files={"media": (path.name, open(path, "rb"))}

# 正确
with open(path, "rb") as f:
    requests.post(..., files={"media": (path.name, f)})
```

检查 `open()`、连接、游标、`ZipFile`、临时文件是否都有 `with` 或显式 `close`。循环里的泄漏比单次调用严重得多。

### 8. 异常吞咽

```python
try:
    ...
except Exception as e:
    errors.append((name, str(e)))   # 调用方的 TypeError 和接口 500 长得一样
```

宽泛 `except` + 只记 `str(e)` 会让**配置错误、代码 bug、外部服务故障**三者无法区分。至少带上异常类型：`f"{type(e).__name__}: {e}"`。

注意：批量任务里"单个失败不中断整体"本身是合理设计，不要一律判为问题——要判的是**失败是否可见**。

### 9. 翻页逻辑

- 首页请求是否传了页码？如果依赖配置里的初始值，配置写错就会**顺序颠倒并重复/漏数据**。
- 终止条件（`more_key` / 空数组 / 页大小）是否覆盖了服务端返回异常的情况？
- 有无无限循环风险：如果服务端始终返回 `more=true` 且数据非空，会不会死循环？建议加页数上限。
- 单页失败是否丢弃了已拉取的页？

### 10. 路径与配置

```python
BASE1 = Path(__file__).parent              # 脚本相对
BASE = Path("/home/ads_fin_user")          # 硬编码绝对路径
CONFIG = Path("./config/x.json")           # 相对当前工作目录 ← 最危险
```

三种混用意味着脚本只能在特定 cwd 下运行。检查：路径是否统一、是否依赖 cwd、硬编码路径在换环境时是否会失效。

### 11. 字符串替换

```python
for k, fn in PLACEHOLDERS.items():
    if k in obj:
        return obj.replace(k, fn(now))   # 命中即 return，后续占位符不再替换
```

检查替换函数是否遗漏了同一字符串内的多个匹配。这类 bug 在"配置里每次只用到一个占位符"时不会暴露。

### 12. 凭据

**明文凭据是 P0，无论是否已有注释承认。** 检查：token、webhook key、密码、鉴权 header 是否硬编码。

要点：如果凭据已提交进 git，**删除当前行不够**，必须作废重建——它已存在于历史中。评审意见里要明确说这一点，不要只说"改成环境变量读取"。

## 三、ETL 静默失败专项

数据任务特有的失效模式，普通 code review 容易漏。逐条过：

| 风险 | 表现 | 怎么查 |
|---|---|---|
| 空结果但任务成功 | `insert overwrite` 写入 0 行，退出码 0 | `NOT IN` 的 NULL；join 写错；过滤条件写反 |
| 主键漂移 | 同一业务产生多条记录 | `md5` 里含时间戳/修改时间 |
| 重复写入 | 下游出现重复数据 | 缺少去重；窗口函数条件写错 |
| 分区写错 | 数据进了错误日期分区 | select 里的分区列与 `partition()` 不一致 |
| 全表扫描 | 任务越来越慢 | 子查询无分区过滤 |
| 全量删除 | 数据凭空消失 | 清理脚本无保留策略（见第 13 条） |

### 13. 清理 / 删除脚本

**无差别删除的脚本一律 P0。** 检查是否按时间保留、是否有 dry-run、是否可能误删非目标内容。

```python
for filename in os.listdir(dir_path):
    ...  # 全删
```

对照该目录 README / 注释里声明的策略（如"保留最近 2 天"）——**代码与声明的策略不一致本身就是问题**。

### 14. 任务编排

- 清理任务和产数任务的**执行顺序**是否明确？并发或顺序颠倒会导致"刚产出就被清掉"。
- 上游产出时间是否早于下游消费时间（跨任务依赖）。
- 重跑是否幂等（`insert overwrite` 是，`insert into` 不是）。

## 四、分级标准

按**后果**分级，不按代码风格。

| 级别 | 判据 |
|---|---|
| **P0** | 静默产出错误数据 / 数据丢失 / 凭据泄露 / 任务成功但结果为空 / 数据被误删 |
| **P1** | 特定条件下出错（边界、跨月、重跑、网络抖动）；或错误不可见导致排查困难 |
| **P2** | 工程规范、可维护性、文档不一致、死代码 |
| **P3** | 命名、格式、个人偏好（**默认不写，除非用户要求**） |

判定 P0 前自问：**这个错会让下游拿到错数据而不自知吗？** 会 → P0。只会报错暴露 → P1。

## 逻辑概述
<用 2-3 句复述你理解的业务逻辑，让作者确认你没读错>

## 问题清单

|---|---|---|---|
| 1 | P0 | 第 12 行 | 一句话摘要 |

### 1. <问题标题>
<位置>

```

````

### 写作要求

- **每条问题说清"为什么"**，具体到后果。"缺少分区过滤"不好，改成"缺少分区过滤：退款表按天分区，每次跑全表扫描，且只要历史分区有一条 NULL，`NOT IN` 会让结果集为空——任务成功但一条都不写"。
- **明确说不成立的事**。核过后没问题的点（如"第 32 行跨月比较是正确的，不用改")要写出来，避免后来人重复怀疑。
- **区分本次引入与历史遗留**。历史问题标注"非本次改动引入，但位于依赖路径上"。
- **结尾给可执行的优先级顺序**，不要列完 13 条就结束。
- **不要凑数**。3 条真问题好过 15 条包含命名建议的清单。

## 六、评审前自检

- [ ] 读了上下游或同类任务，不是孤立看一个文件
- [ ] 每条问题都有 文件:行号 + 代码片段
- [ ] 每条 P0 都能说出具体的错误后果
- [ ] 拿不准的放进了"待确认"，没有硬判成 bug
- [ ] 核过没问题的点也写了（避免后人重复怀疑）
- [ ] 区分了本次引入和历史遗留
- [ ] 给了优先级顺序
- [ ] 没有为了凑数写 P3 风格建议
- [ ] 核心逻辑没问题时，明确说了"没问题"

## 七、边界

- 不评业务口径是否正确 —— 只标出"此处需业务确认"
- 不评 DDL / 数据模型 —— 用 `dba-schema-review`
- 不做性能压测、不跑真实数据验证 —— 结论基于静态阅读
- 不评算法与模型选型
