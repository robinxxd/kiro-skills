## 这个 Skill 做什么

给数据库设计加一层专业评审视角。用于任何**引入或修改数据库表 / 数据模型**的变更：建表、改字段、加索引、写迁移。

## 何时使用

- 变更里含 `.sql` 文件
- 有数据模型 / 建表 / schema 相关章节的设计文档
- 评审迁移脚本

不适用：概念数据模型讨论（有哪些实体、什么关系）；那属于产品需求层面。

## 一、评审清单

### 架构层面

1. **单库多域** — 一个物理库，每个域用独立 schema。新表必须落在本域 schema，不得裸放公共 schema
2. **跨域只按 ID 松引用** — 不做跨 schema 外键；跨域引用存对方主键 ID，由应用层解析。共享实体（标识、审计）放 shared schema

### 列约定

3. **枚举用 `text + CHECK`**，不用原生 enum —— 生产库改枚举类型会阻塞
4. **时间列一律用带时区的类型**（如 `timestamptz`），命名 `_at`；主键用时间有序的 UUID（如 UUIDv7，利于游标分页）；外键命名 `_id`；统一 snake_case
5. **软删除统一 `deleted_at`**；内容寻址 / 大对象用引用计数 + GC，而非直接删
6. **不变量由约束保证**，关键约束旁标注编号，不靠应用自觉（如"归属容器非空" = NOT NULL）

### 性能

7. **索引对齐查询模式** — 列表、时间线、游标分页要有对应（部分）索引；高基数过滤列建索引；避免无用索引
8. **可见性 / 权限过滤列物化**（如 `effective_visibility`）并建索引，所有权限查询走它

### 工程与治理

9. **迁移** — 一个域一套迁移目录，归属该域 owner；破坏性变更标注；大表变更评估锁与在线性
10. **命名 / 注释** — 表列用注释说明用途与不变量引用

## 二、两条脑裂事故防线（最重要）

下面两条都是从真实事故提炼的，是整份清单里最容易踩、后果最隐蔽的部分。

### 第 11 条 · 建表前查重（防同仓脑裂）

任何 `CREATE TABLE` 必须先检索**主分支迁移目录**是否已有同名或近似名表，**包括单复数变体**：

```
birthday_preference  vs  birthday_preferences
```

已存在 → 必须 `ALTER` 扩展现有表，**禁止**新建平行表。

> 真实案例：两个几乎同名的表被分别创建，数据写进不同表，功能时好时坏，排查成本极高。

### 第 12 条 · 跨仓 schema 所有权（防产品级脑裂）

**一个业务实体的物理表只能有一个 owner 仓。**

评审含建表的变更时，必须确认该实体是否已在**其他仓**有权威表，或被架构决策冻结了所有权。其他仓需要该数据 → 调 owner 仓的 API，**禁止**在自己库里再建一套同语义表。

> 真实案例：某服务在另一个库平行建了同名的公告表，导致**管理端发的公告终端读不到**。不是报错，是静默的数据割裂——两边都能用，互不可见，测试阶段极难发现。

## 三、评审产出

逐条给「**过 / 不过 + 原因 + 建议**」。不过的点必须**具体到表 / 列 / 约束**，不要笼统说"规范不符"。

产出格式：

```
结论: <通过 / 要求修改>
要点:
- [表名.列名] <问题> → <修法>
- ...
证据: <文件:行 / 迁移文件>
```

## 四、评审前的自检（提变更前）

- [ ] 新表已在本仓迁移目录查重（含单复数变体）
- [ ] 该实体在其他仓无权威表、无所有权冻结
- [ ] 新表落在本域 schema，未裸放公共 schema
- [ ] 跨域引用存 ID，无跨 schema 外键
- [ ] 枚举用 text + CHECK，未用原生 enum
- [ ] 时间列带时区、命名 `_at`
- [ ] 主键为时间有序 UUID，外键 `_id`
- [ ] 软删字段统一为 `deleted_at`
- [ ] 关键不变量有约束兜底，非仅应用层校验
- [ ] 索引对齐实际查询模式
- [ ] 迁移脚本标注破坏性变更
- [ ] 表列有注释说明用途

## 五、边界

- **概念数据模型**（有哪些实体、什么关系）属产品需求层面
- **物理 DDL、索引、单库约定**属本 skill 的范围
- 只管物理设计与单库规范，不评业务语义是否合理
