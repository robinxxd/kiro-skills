## 这个 Skill 做什么

把需求（PRD / 接口契约 / 设计稿）转成可执行、可验证的测试用例，并且守住几条容易翻车的质量红线：断言太浅、权限用例糊弄、写恒真空断言。

## 何时使用

- 拿到需求要写测试用例
- 审查既有用例的质量
- 设计验收标准，需要判断"这条能测吗"

不适用：跑测试（用例写完之后的事）。

## 一、优先级分级

| 优先级 | 标签 | 定义 | 通过要求 |
|---|---|---|---|
| P0 | 冒烟 | 核心功能不可用即阻断发布 | 100% |
| P1 | 核心 | 主要业务场景、高频使用 | ≥95% |
| P2 | 次要 | 低频功能或辅助流程 | ≥80% |
| P3 | 边界/体验 | 边界条件、异常场景、视觉还原 | 尽力 |

**P0 判定规则**（满足任一即 P0）：

- 用户无法完成核心业务流程
- 数据丢失或损坏风险
- 影响超过 50% 用户
- 安全问题（越权、XSS、敏感信息泄露）

## 二、断言分层（最容易出问题的地方）

**只断言 HTTP 状态码视为不合格。** 这会掩盖"状态码对但行为错""状态码与设计冲突"这类真实问题。

每条用例的预期结果至少覆盖相关层：

| 层级 | 断言内容 | 示例 |
|---|---|---|
| 状态码 | HTTP status | 201 / 422 |
| 响应体结构 | 字段存在性 + 类型 | `body.id` 存在且为 string |
| 业务语义 | 状态机、字段值 | `status=active`、`author_id` 为当前用户 |
| 错误码 | 契约定义的业务错误码 | `target_not_found`、`reply_depth_exceeded` |
| 集成副作用 | 跨服务是否触发 | 通知已发、积分已发、审核已入队 |
| 持久化 | 数据库状态变化 | 仅一条记录、软删占位保留 |

### 必须断言的八条

1. **错误场景必须断言业务错误码** — 不能只写 HTTP 状态码
2. **状态码与契约一致** — 设计规定 422 就别写 400，生成时核对错误码章节
3. **错误体格式遵循契约** — 若规定了 problem+json，断言 `type` / `title` 存在
4. **权限用例逐角色断言** — 作者 200、管理员 200、普通用户 403、跨租户 403，禁止合并成"验证权限"一句话；前置条件必须写明每个角色的身份与上下文
5. **集成副作用必须断言** — 不只验 HTTP 响应
6. **幂等性断言资源标识一致** — 重放返回相同 `id`，而非仅 200
7. **软删/占位必须断言** — 若设计保留占位，断言状态值、占位文案、关联可见性、审计字段
8. **计数/列表断言语义** — 计数不含软删记录；列表断言排序、分页结构、层级关系

## 三、禁止恒真空断言

**最隐蔽的测试缺陷：mock 返回值与原实现相同、测试永远绿，等于没测。**

- 断言必须能随行为破坏而变红（先红后绿）
- 删测试或改写断言需说明原因
- 自检：如果我把被测逻辑改坏，这条会失败吗？不会，就是空断言

## 四、冗余用例检查

生成后必须做一轮精简，目标是**数量减少 30%-50%，保持 100% 功能覆盖**。

| 检查项 | 处理方式 |
|---|---|
| 重复功能覆盖 | 合并为一个用例，覆盖多个验证点 |
| 前置条件重复 | 删除或合并；如"未登录用户"已在其他用例隐含验证 |
| 权限测试重复 | 每类接口仅保留一个权限测试代表 |
| 集成测试重复 | 集成测试只验跨服务调用，不重复验接口功能 |
| 边界测试重复 | 相同边界条件只出现一次 |

## 五、输入依据要求

**所有用例必须有明确的输入依据，禁止捏造或推测。**

每条用例标注来源，至少一项：

- 需求条款编号（FR-1.1、AC-1）
- 接口契约（`POST /api/v1/likes`）
- 设计稿页面 / 元素
- 数据约束（如"评论长度 ≤ 2000 字符"）
- 错误码定义
- 权限矩阵

**禁止**：捏造未定义的接口、推测未明确的数据约束、添加未提到的错误码、臆造未定义的权限场景。

## 六、未知场景处理

遇到文档未覆盖的场景：

1. **不生成用例** — 只生成有明确依据的
2. **标注待确认** — 在文末列出，格式：

```markdown
## 待确认场景

以下场景在输入文档中未明确，需与产品/设计确认：

1. **场景描述** — 来源：{缺失项}
   - 建议补充到需求文档
   - 或明确标注为"暂不支持"
```

## 七、用例模板

### API 用例

```markdown
### [API-001] 用例标题
**优先级：** P0
**来源：** FR-1.1
**接口：** POST /api/v1/example
**请求参数：** {字段: 值}
**前置条件：** <每个角色的身份与上下文>

**预期结果：**
- 状态码：201
- 响应体：`body.id` 存在且为 string
- 业务语义：`status=active`
- 集成副作用：通知已发送

**验证方式：** 自动化 / 手工
```

### UI 用例

```markdown
### [UI-001] 用例标题
**优先级：** P0
**来源：** 设计稿-详情页 / FR-1.1
**页面路由：** /path/to/page
**前置条件：** <状态>

**步骤与预期：**

| 步骤 | 操作 | 预期结果 |
|---|---|---|
| 1 | 打开页面 | 元素 X 可见，状态为默认态 |
| 2 | 点击 Y | 弹层出现，文案为 Z |

**状态变体：** 默认 / 悬停 / 聚焦 / 禁用 / 加载 / 错误 / 空
```
